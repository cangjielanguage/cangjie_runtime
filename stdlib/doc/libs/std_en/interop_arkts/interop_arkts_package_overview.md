# std.interop.arkts

## Introduction

The interop.arkts package provides the standard-library preset types for ArkTS interoperability, so that `@ArkTS` declarations can refer to them across the boundary (this version ships the member implementations of `ArkTSArray<T>` and `ArkTSString`; see the signature-position rule below):

1. `ArkTSType`: the root interface of all ArkTS interop types, by design mapped bidirectionally to the ArkTS `unknown` type;
2. `ArkTSArray<T>`: the Cangjie-side type of an ArkTS `Array<T>`/`T[]` object;
3. `ArkTSString`: the Cangjie-side type of an ArkTS `string`;
4. `ArkTSFunc<F>` and `ArkTSFuncWithThis<ThisT, F>`: the Cangjie-side types of ArkTS function values;
5. `ExternConversionException`: the named exception thrown when a cross-boundary conversion fails, an ordinary public class and not one of the preset external ArkTS types above.

The compiler treats this package as a preset declaration package: `ArkTSArray`, `ArkTSString` and `ArkTSType` declared in `std.interop.arkts` are recognised as the preset external ArkTS types; declarations with the same names in other packages stay ordinary types and are unaffected.

`ExternConversionException` is hosted by this package: the generated preset wrapper bodies (which are part of this package) name the type directly with no import, and the `arkts.lang` facade re-exports it to applications through its `public import std.interop.arkts.*`; the facade does not declare the type itself. Declaring it in the facade would force the preset wrappers to import `arkts.lang`, which depends on this package, i.e. a same-package cycle. Note that `std.core`'s `Extern` mechanism also exports an exception of the same name (present when `env != "ohos"`): a name reached through this package or the facade via an explicit import takes precedence over the implicitly pre-imported `std.core`; compiler-generated code always binds the name through a single-member import with a private alias and is unaffected.

This version ships member implementations: the `ArkTSString` member bodies are generated by the compiler onto the prepared wrapper, and the `ArkTSArray<T>` member bodies are implemented by this package's source (the compiler installs the reference storage), so the build produces and installs `std.interop.arkts.cjo` and a static library. `ArkTSType` and `ArkTSFuncWithThis` keep their declaration forms; the static members and the remaining designed members arrive in a later release, and the library targets return with them.

This version delivers the reference semantics and the member-level conversion for `ArkTSArray<T>` and `ArkTSString`: both map when they appear in an `@ArkTS foreign` signature position (a parameter, the return value, or a nested position), with element/content conversion through the `JSInteropType` runtime contract and the `ctx.string` construction respectively. The `ArkTSType` signature mapping is still deferred: when it appears in such a position, the compiler rejects the usage and reports that the reference semantics of that type is not available in this version. `ArkTSFunc` and `ArkTSFuncWithThis` are not among these three preset types and do not follow that path; their signature positions are rejected as ordinary unsupported types, with a position-specific message.

Cross-boundary runtime contract: interoplib (`ohos.ark_interop`) guarantees the rooting of temporary `JSValue` values and the translation of ArkTS exceptions into Cangjie exceptions; generated interop code does not insert explicit root operations, but it wraps cross-boundary calls in `try/catch (BusinessException)`: only an external-library error code or an ArkTS-side throw is translated into a Cangjie exception and rethrown, while the other `BusinessException`s keep their type, error code and message and are rethrown as-is. GC root registration and release, cross-language ownership, and thread constraints are defined in a later release and are not defined in this version.
